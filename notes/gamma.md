# GAMMA (MO2) launching and differences
- `C:\GAMMA` is only the MO2 folder (no fsgame.ltx, no bin): MO2 `gamePath` = `C:\Anomaly`; mods are loose dirs `C:\GAMMA\mods\<name>\gamedata` overlaid by usvfs into `C:\Anomaly`; profile `G.A.M.M.A` (modlist.txt), overwrite `C:\GAMMA\overwrite`.
- Supervisor launch (goal 24): game_launch(game_root=C:\GAMMA) = `ModOrganizer.exe -p <ini selected_profile> run <exe> -a "-fsltx <ini gamePath>\fsgame.ltx -appdata <slot> -mcp_port 0"` (`mo2_setup`/`mo2_run`); game = MO2's child (toolhelp ppid), then our MO2 is killed. Default build exe from `_build\_game\bin_dbg` works (overlay + GAMMA-only files resolve); timings: launch ~44-46 s (port ~30 s), new game ~32 s, level change ~13 s, in-game load ~12 s, restart ~48 s.
- MO2 starts the game with CREATE_BREAKAWAY_FROM_JOB: inside a job that forbids breakaway (the MCP Python SDK stdio client puts its server in one) it fails `Error 5 ERROR_ACCESS_DENIED` with a modal box. So MO2 is started with explorer.exe as parent (`spawn_outside_job`, PROC_THREAD_ATTRIBUTE_PARENT_PROCESS); an `E] Error N`/`Failed to run` line in `C:\GAMMA\logs\mo_interface.log` (rewritten per start) kills our MO2 at once.
- The MO2-started game is already in MO2's job; our KILL_ON_JOB_CLOSE job must be a fresh one per game (a job nested under one job's hierarchy cannot take a process of another: error 5). Verified: killing the supervisor kills the GAMMA game.
- Killing our own MO2 right after the game child appears (~3.3 s) is reliable (3/3): port after ~30 s, new game ~31 s, mod files still resolve, graceful quit. usvfs lives in the game process; no usvfs_proxy helper seen.
- Gotcha (why game_launch refuses while any MO2 runs): starting another MO2 `run` while a GAMMA game is still in startup (OnAppStart; the MCP port is up before it ends) crashed that game: once usvfs __fastfail (WER dump), once FATAL "can't open file character_dialogs.xml" (usvfs rebuilt its shared tree). A game already in a level survived a second launch. Serialize GAMMA launches until the previous one reached the main menu.
- Writes under MO2: -appdata dir gets logs/saves/shaders_cache/user.ltx and, since goal 24, axr_options.ltx (engine redirect with -mcp_port, see gamestate.md; before, options/new-game config went into the GAMMA mod file `G.A.M.M.A. MCM values ...\gamedata\configs\axr_options.ltx`); nothing new lands in `overwrite`; MO2 rewrites its profile files (same content) and ModOrganizer.ini UI state on start/exit.
- Mute: `zzz_player_injuries` sets `snd_volume_eff` from `ui_options.get("sound/general/master_volume")` (axr_options [options], GAMMA's is 1) on every actor_on_first_update. Launch writes 0 into the slot's axr_options copy (`MUTE_LUA`), so the mod applies 0: verified 0 after new game, level change, game_load, no per-load command. Vanilla never applies master_volume from options (only the cvar/user.ltx).
- game_load: GAMMA's TutorialMonitor keeps a tutorial (tutorial_sleep) active all the time; SL_LOAD only stops a tutorial when the actor is dead (death screen), else game_load never issued the load and timed out.
- Differences: first new game load ~31-39 s (vanilla ~12-13 s), later level loads 13-16 s; 8 non-fatal script load errors from the mod list itself (a_faction_prices, mags_patches, zz_ui_inventory_better_stats_bars, zzz_mspizza_godis_zoomcalc); stalker kit 29 items / 5000 RU without a pistol; Fanatic's task is esc_2_12_stalker_fanat_task_3 (clear mutants in y04_pole).
- `Reload Unjam Same Key Fix` mod keeps wpn_reload on kR; injected `reload` fires `on_before_key_press`/`on_key_press` (dik 19, bind 34) and refills the mag, same as vanilla.
- Memory (template user.ltx, private bytes / per-process dedicated VRAM via perf counter `\GPU Process Memory(pid_N*)\Dedicated Usage`; nvidia-smi per-process is N/A under WDDM): GAMMA main menu 5.3 GB / 3.1 GB, Cordon 10.6 GB / 7.0 GB (GPU total 7.6 of 8 GB); vanilla Cordon 4.1 GB / 1.6 GB.
